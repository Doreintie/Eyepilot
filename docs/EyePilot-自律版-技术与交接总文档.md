## A0 · 先承认三件事做不到

| 做不到 | 为什么 | 硬数据 | 处置 |
|---|---|---|---|
| **可靠的情绪识别** | RGB 摄像头分不清"皱眉思考"和"皱眉生气"；亚洲人表情幅度偏小 | 最好的开源模型 HSEmotion `enet_b2_8` 在 AffectNet 八类 **63.0%**、七类 **66.3%**；FocusTrack 自训 CNN **59.28%**；人类在 FER2013 上约 **65%** | **不叫"情绪识别"，改叫"面部状态占比"**，只在报告里给分布，不给结论 |
| **靠眼神判断所有走神** | 眼睛必须可见。低头写字时摄像头只能看到头顶 | 低头时段 G1/G2 全部失效 | **低头时段只统计、不下结论**，见 A2 |
| **实时精确判定"发呆"** | 发呆没有正向动作，只有"动作停止"这个负向特征 | 注视凝固只在直视屏幕时有效（约 8 秒窗口） | **只做"看着屏幕但不读"这一种发呆**，低头时段一律不下结论 |

> 这三条不要试图硬做。花两天把 63% 的情绪模型接进来，不如花半天把头姿基线做准。**后者评委一看就懂，前者怎么讲都心虚。**

## A1 · 关键转向：从"读表情"到"读动作"

表情和眼神都是**小位移、高噪声**信号：虹膜在 640×480 下只有 10px，表情分数在 0.1 附近浮动。

动作是**大位移、低噪声**信号：抬手是几十到上百像素，低头是 20 度以上。

| | 表情 / 眼神 | 动作 |
|---|---|---|
| 信号幅度 | 像素级 | 几十像素到整屏 |
| 噪声 | 高（虹膜抖动、表情漂移） | 低 |
| 需要校准 | 部分是 | **完全不需要** |
| 需要训练 | 是（且只有 63%） | 否（规则即可） |
| 可解释性 | "模型输出 0.71" | "你的手停了 15 秒" |
| 答辩可讲性 | 弱 | **强** |

**结论：动作检测是这次最该投入的地方。** 它同时满足"准确、免校准、可解释、好演示"四个条件，而表情一个都不满足。

## A2 · 只有一种场景：人正对屏幕

**不设场景选择。** 打开就学，摄像头在屏幕上方，正对你的脸。这个决定是为了砍掉一整条做不通的支线。

### 为什么不做手部

有一版方案想靠「手」来判断状态：写字时手在动，停笔 15 秒就是卡住或走神。逻辑很漂亮，落地有四道坎：

| 坎 | 具体问题 |
|---|---|
| 拍不到 | 笔记本摄像头在屏幕上方，写字的手在桌面下方，大概率整个出画 |
| 太贵 | 手部模型实测 25.5ms/帧，吃掉三分之一帧预算，换来的只是一个二值判断 |
| 分不开 | 手停了 15 秒，可能是卡住，也可能在认真思考。误报一次，用户就不信这个产品了 |
| 场景窄 | 它的价值全押在纸笔学习上，而纸笔学习恰恰是最拍不到手的那个姿势 |

四条加起来，结论很清楚：**砍掉。** 把预算全给眼睛和头。

### 留下来的是什么

| 信号 | 判据 | 含义 |
|---|---|---|
| 眼头不一致（G1） | 眼内偏移超基线 ±3σ 持续 2 秒 | 眼睛飘走了 |
| 注视凝固（G2） | 8 秒内跳视 < 5 次且眼不偏 | 盯着不读 |
| 眨眼节律（G3） | 双向异常 | 走神型 / 疲劳型 |
| 头姿（F2/F3） | yaw / pitch 偏离基线 | 转头、抬头、低头 |
| 肢体（F12） | 举手、挥手、伸懒腰、撑头、趴桌、起身 | 身体状态，不进专注率 |
| 离座 | `present === false` | 最确定的分心 |

### 模型频率

没有场景切换，频率就写死一组，配合 A4 的单槽队列：

```js
const RATE = {
  face:   30,   // 每帧都跑，这是主信号
  pose:    1,   // 1 秒一次，够抓伸懒腰 / 趴桌
  object:  1,   // 1 秒一次，看手机在不在画面里
};
```

手部模型不加载，省下的 25ms 全部留给渲染和姿态。

## A3 · 可统计动作清单（哪些能做，哪些别碰）

| 动作 | 判据 | 依赖 | 可靠性 | 难度 | 建议 |
|---|---|---|---|---|---|
| 离座 | `present=false` > 2s | Face | 高 | 已有 | ✅ 必做 |
| 低头 | `pitch` 稳定在 +15°~+45° | Face | 高 | 低 | ✅ 必做 |
| 转头 / 视线游移 / 打盹 | 见 F2 阈值表 | Face | 高 | 低 | ✅ 必做 |
| 伸懒腰 | 双腕**同时**高于肩线，持续 1.2 秒 | Pose | 高 | 低 | ✅ 已做（F12） |
| 举手 / 挥手 | 单腕高于肩线；腕部横移 2 秒内往复 3 次 | Pose | 高 | 低 | ✅ 已做（F12） |
| 撑头 / 托腮 | 腕到鼻距离 < 0.55×肩宽，持续 2 秒 | Pose | 高 | 低 | ✅ 已做（F12） |
| 抱臂 / 叉腰 | 两腕交叉；腕贴近同侧髋（髋可见时） | Pose | 中高 | 低 | ✅ 已做（F12） |
| 趴桌 | 鼻低于肩线，持续 3 秒；超 3 分钟转暂停 | Pose | 高 | 低 | ✅ 已做（F12） |
| 含胸 | 鼻到肩线距离比基线低 0.2，只统计占比 | Pose | 中 | 低 | ✅ 只统计占比，不出事件（F12） |
| 久坐 | 四肢 4 点位移能量低，持续 10 分钟 | Pose | 中高 | 低 | ✅ 健康提醒（F12） |
| 看手机 | COCO `cell phone` 检测 + 低头 | Object | 中 | 中 | ⭕ 手机入镜才算 |
| 停笔 / 翻页 / 喝水 / 摸脸 | 需要手部 21 点 | Hand | — | — | ❌ **已砍**，理由见 A2 |
| 转笔 | 指尖轨迹圆形度 + 周期性 | Hand | — | — | ❌ 已砍，需要自采数据训分类器 |
| 抖腿 | 需要看到下半身 | — | 不可行 | — | ❌ 放弃 |
| 桌下玩手机 | 手机不在画面里 | — | 不可行 | — | ❌ 放弃，只能靠低头推断 |

**两条必须说清的边界**：

1. **看手机**这个统计的真实含义是"低头 + 手机入镜"。用户把手机放在桌下刷，摄像头拍不到，只能靠 `pitch` 推断，所以报告里必须写"低头（可能在看手机）"，不能写"看了 3 次手机"。
2. **手部那一整套全砍了**，包括停笔、翻页、喝水、摸脸、撑头（旧版）。撑头保留在 F12 里，用的是姿态模型的腕和鼻，不需要手指关键点。这条要写进答辩准备，被问到"为什么不看手"时，答案在 A2。

## A4 · 模型选型（全部开源、全部可本地跑）

### 关键前提：不用再引任何新运行时

现有 `vendor/mediapipe/vision_bundle.mjs` **已经导出了下面全部三个会用到的类**，我验证过：

```
PoseLandmarker  ObjectDetector  FaceLandmarker
```

也就是说，**不需要装 onnxruntime-web，不需要第二个推理引擎，只要再下几个 `.task` 模型文件。**

| 任务 | 模型 | 体积 | 浏览器 | 精度 | 结论 |
|---|---|---|---|---|---|
| 人脸 / 眼 / 头姿 / 眨眼 | MediaPipe **Face Landmarker** | 3.6MB | ✅ 已有 | 高 | **保留，主信号** |
| 身体 33 点 | MediaPipe **Pose Landmarker**（lite） | 5.8MB | ✅ 同一运行时 | 高 | **已用（F12）**，举手/挥手/伸懒腰/趴桌/久坐，只认动作不算角度 |
| 物体 80 类 | MediaPipe **EfficientDet-Lite0**（int8） | 4.6MB | ✅ 同一运行时 | 中（COCO mAP 约 25 量级） | **够用**，手机/水杯/书/笔电都在 COCO 里 |
| 手部 21 点 | MediaPipe Hand Landmarker | 7.5MB | ✅ 同一运行时 | 高 | ❌ **不加载**，理由见 A2 |
| 更高精度物体检测 | **YOLO11n**（ONNX） | ~5.4MB | ⚠️ 需 onnxruntime-web | 较高（COCO mAP 约 39 量级） | 只在 Lite0 明显不够时换，会多引一个运行时 |
| 表情（如果一定要做） | **HSEmotion** `enet_b2_8`（ONNX） | ~15MB | ⚠️ 需自己接预处理 | AffectNet 八类 **63%** | **不建议**，见第 0 节 |

> 体积与 mAP 是官方公开数据的量级参考，接入前用你们自己那台机器实测一次帧率，别信纸面数字。

**为什么优先用 MediaPipe 的 EfficientDet 而不是 YOLO**：多一个运行时就是多一条部署链、多一份现场翻车风险。而且你们要做的是"手机有没有出现在画面里"这种大目标检测，不需要 YOLO 的精度。**5 个百分点的 mAP 换一个 onnxruntime-web，不划算。**

### 性能预算：必须分频，不能每帧全跑

30fps 下每帧只有 33ms。下表「实测」一列是 2026-11-27 在本机用无头浏览器跑出来的真实数字（640×480、IMAGE 模式、软件 GL，属于**悲观下界**，真机 GPU + VIDEO 模式会快 30%~50%）：

| 模型 | 频率 | 单帧耗时（估） | 单帧耗时（实测） | 摊到每帧 |
|---|---|---|---|---|
| Face | 30fps | 10~20ms | — | 15ms |
| Pose | 1fps | 10~15ms | **36.6ms** | 1.2ms |
| Object | 1fps | 10~20ms | **88.6ms** | 3ms |
| **合计** | | | | **约 19ms，留 14ms 渲染** |

**三个模型都能从同一个 `vision_bundle.mjs` 加载，不需要第二个运行时，这一条已经实测确认**（`PoseLandmarker` / `HandLandmarker` / `ObjectDetector` 全部 createFromOptions 成功，模型加载 0.3~1.0 秒）。

砍掉手部之后预算宽松了不少（原来 28ms，现在 19ms），但实测仍推翻了初版估算：**姿态 37ms、物体 89ms，比文档初版写的数字高两到四倍。** 结论有三条：

1. **频率要按实测定。** 姿态 1fps，物体 1fps 就够（手机在不在画面里不会一秒变一次）。
2. **不能在同一帧里叠两个大模型。** 姿态 37ms 加物体 89ms 就是 126ms，必然卡住。要用一个**单槽任务队列**：每帧只允许跑一个「非 Face」模型，按到期时间轮转。
3. **如果三个模型都跑 30fps，总耗时 130ms 以上，直接掉到 7fps。** 分频调度是硬要求，不是优化项。

```js
// 单槽队列：一帧最多一个大模型，跑不下的顺延到下一帧
const queue = new PriorityQueue(['pose', 'object']);
function onFrame(now) {
  face.detectForVideo(video, now);          // 每帧必跑
  if (now - lastSlot < 33) return;          // 上一帧刚跑过，这帧只跑 face
  const job = queue.next(now);              // 按各自频率到期的那个
  if (job) { job.run(); lastSlot = now; }
}
```

## A5 · 需要你们采数据 / 调参的，只有两件

手部砍掉之后，原来最麻烦的两件事（停笔阈值、转笔分类器）一起消失了。剩下两个标定项，加起来不超过一小时。

### ① 眼动基线（半天，两个人各 10 分钟）

让 2 个人各正常学习 10 分钟，把 `ex / ey`（眼内偏移）序列导出，看两件事：

- 基线的 `stdEx` 有多大。**如果大于 0.04，先解决硬件和光线，不要调阈值**，因为噪声已经大过信号了。
- 10 分钟里 `GAZE_DRIFT` 触发了几次。真人正常学习应该是 **0 到 2 次**，超过 5 次说明阈值太松。

### ② 姿态基线（半小时，两个人各 5 分钟）

导出 `headDrop` 和 `limbEnergy` 两条序列：

- `headDrop` 正常坐姿大概落在 −0.6 到 −0.8。**如果两个人的基线差超过 0.15，就不要用全局阈值**，改成每人会话开始前 30 秒取中位数当基线，判「比基线低 0.2」。
- `limbEnergy` 静息值有多大。如果静息就有 0.005 以上，`sedentaryEnergy` 要跟着放大，否则久坐提醒永远不触发。

> 这两件事的共同点：**量的不是"人"，是"这台摄像头在这间屋子里的噪声底"。** 换一台机器就要重做，所以文档里所有阈值都当成初值，不当成定论。

## A6 · 护眼：模块保留，指标按低头与否切换

护眼是这个项目最早的东西，也是答辩时最不容易被挑的部分，全部保留。

| 指标 | 做法 |
|---|---|
| 视距 | 默认用瞳距估算；**低头时瞳距会被压缩，必须改用脸框宽度兜底**，否则会算出"距离 90cm"这种假数据 |
| 低头时长 | 连续 > 20 分钟提示颈椎，这是护眼的主力指标 |
| 连续用眼 | 45 分钟提醒休息 |
| 眨眼频率 | 低头时数据无效，只在头抬起时采 |
| 远眺提醒 | 20-20-20，每 20 分钟一次 |

> 「低头时视距算不准」这条一定要写进代码，不能只在文档里说。做法：`pitchDeg > 25` 时把 `distanceCm` 标记为不可信，UI 显示"--"而不是一个错数。**宁可没有数，也不要给一个假数。**

## A7 · 报告里能写什么，不能写什么

| 能写 | 不能写 |
|---|---|
| 「低头 42 分钟，其中视线离开屏幕 6 次，最长一次 2 分 10 秒」 | 「你走神了 6 次」 |
| 「伸懒腰 3 次，撑头 2 次」 | 「你今天情绪低落」 |
| 「面部状态：平静 78%、皱眉 15%、放松 7%」 | 「你的压力指数 63」 |
| 「被打断 7 次，每次重新接上平均要 20 分钟以上」（附文献） | 「你损失了 2.5 小时深度专注」 |
| 「离座 2 次，共 4 分钟」 | 「自律评分 62 分，超过 38% 用户」 |

**最后一条尤其注意**：25 分钟的会话里不可能损失 2.5 小时，这种乘法一算就崩。而且原研究量的是"回到原任务的时间"，不是"恢复专注深度的时间"。引用要克制。

## A8 · 答辩怎么说（这段直接背）

> "我们只统计能看见的东西。
>
> 你低头、你转头、你眼睛飘走、你离座、你伸懒腰，这些是动作，动作骗不了人，也不需要校准。
>
> 至于你在想什么，我们不做判断。市面上说能读情绪的，用的模型在公开数据集上也就六成准确率，比抛硬币好一点。**我们宁可少说一句，也不编一个数字。**"

这段话有两个作用：**把技术短板转成诚实标签**，同时暗示"我们知道那些产品在吹"。评委听到这里通常会点头。

## A10 · 做不做的判断标准

只一条：

> **这个功能能不能变成报告里一句用户在意的话？**

能，就做。不能，不管技术上多酷，都是负资产：它占开发时间、占答辩时间，还会在评委追问时暴露短板。

用这条标准去量：

| 功能 | 能产出的那句话 | 判断 |
|---|---|---|
| 眼头不一致 | "有 3 次你的眼睛离开屏幕超过 2 秒" | ✅ 会在意 |
| 抬手次数 | "你抬手 4 次，最长一次盯着屏幕外的角落看了 6 秒" | ✅ 会在意 |
| 情绪分析 | "你的挫败指数 0.62" | ❌ 不在意的假数字 |
| 转笔统计 | "你转了 12 次笔" | ❌ 有趣但无用 |

### 四个难点的取舍

| 难点 | 值不值得 | 理由 | 怎么处置 |
|---|---|---|---|
| **情绪分析** | ❌ **砍** | 63% 的准确率只支撑得起一句"仅供参考"，却要吃掉两天 | 保留报告里"面部状态占比"一行，用现有 blendshape 直接算，**不接任何模型** |
| **发呆检测** | ⚠️ **打折** | G1（眼头不一致）值得，因为它进专注率；G2（注视凝固）只值一个标签 | 只做 G1，G2 有时间再说 |
| **手部动作** | ❌ **砍** | 摄像头拍不到写字的手，模型还贵，判据本身也分不清"卡住"和"思考" | 全部砍掉，理由见 A2 |
| **性能** | ✅ **必须** | 它不是功能，是前提。不分频就直接跑不动 | 分频调度写成代码约束，帧率低于 20 立刻关 P2 模型 |

一句话：**五条里砍两条、打折一条、两条必做。**

### 五个便宜的增量建议（按性价比排）

**① 恢复时间：把那条用不了的文献变成自己的指标**

Mark 的 23 分钟不能抄（那是别人的数据，且量的不是"专注深度"）。但可以测自己的：

```js
// 一次分心事件结束后，专注度回到该次分心前水平的 90% 所需时间
// 只统计 ≥30 秒的分心，避免噪声
const recoveryMs = timeToReach(0.9 * beforeScore);
```

报告里写：「7 次分心里，4 次你在 30 秒内就拉回来了，最长一次花了 6 分半。」

**这句话的力量在于它是关于"你"的**，不是引用别人的平均数。而且它顺手把"打断有代价"这件事讲清楚了，不用编任何数字。

成本：半天，纯计算。

**② 卡点聚类：从"计数"升级到"归因"**

现在报告说"你分心 7 次"，用户看完不知道该改什么。把事件按时间聚成簇（间隔小于 3 分钟算同一簇）：

> 「你的分心集中在第 12–18 分钟和第 31 分钟之后。前一段你盯着一页看了很久，可能是卡住了。」

一句话就把"你不专心"变成"你卡住了"。这是产品态度的分界线。

成本：2 小时。

**③ 骨架剪影回看：报告里放火柴人，不放照片**

不存任何照片，只存 33 点身体关键点的坐标。报告里画三个火柴人：最专注时的姿势、最散的时候的姿势、平均姿势。

- **隐私安全**：骨架还原不出人脸，比截图安全一个量级
- **视觉冲击**：一张图就能让评委看懂"你塌下去了"
- **和"不录像"的主张一致**：你们敢说"我们只存骨架"，这句话很硬

成本：半天（含画图）。

**④ 专注指纹：一次会话一张波形图**

横轴时间、纵轴专注度，配色渐变，形状像指纹。可导出 PNG 分享。

它同时干三件事：报告的可视化主体、朋友圈传播素材、答辩 PPT 的封面图。

成本：3 小时，数据现成（时间轴已经在算了）。

**⑤ 状态驱动休息：把番茄钟从"定时"改成"看状态"**

不再固定 25 分钟。检测到专注度连续 3 分钟低于 50，才提议休息（不强制，可关）。

这是和所有番茄钟类产品最直接的差异点：**别人按时间提醒，我们按状态提醒。** 一句话能讲清，评委也容易记住。

风险是打断，所以只在"连续下降"时提议，单次会话最多提 2 次。

成本：半天。**时间不够就砍，它的价值主要在叙事。**

### 明确不要做的

| 不做 | 为什么 |
|---|---|
| 云端排行榜、多用户 | 要后端、要用户量，数据一定是假的。评委一问就崩 |
| 真实情绪模型 | 见第 0 节，63% 撑不起任何结论 |
| 录视频回看 | 和"不上传、不落盘"的隐私主张直接冲突 |
| 转笔分类 | 收益一行字，成本一天 |
| 手机 App / 小程序 | 黑客松现场没人愿意装包，扫码即用才有意义 |

#### 规则

| 规则       | 说明                                                                                           |
| -------- | -------------------------------------------------------------------------------------------- |
| 时长预设     | 25 / 45 / 60 / 90 分钟 + 自定义（5–180）                                                            |
| **不选场景** | 用户点开始就开始，不让他先做选择。所有引擎按 A2 的 `RATE` 常开，眼神、头姿、肢体一起跑 |

| 提前结束     | 允许，但报告标注「提前结束」，不计入连续专注纪录                                                                     |
| 自动结束     | 倒计时归零 → 自动生成报告                                                                               |

### F2 · 分心识别引擎（核心）

#### 目标

把每秒的 `frame` 判定成"是否在分心"，输出带起止时间的事件流。**这是整个产品的技术核心。**

#### 输入

```js
frame = {
  t, present,          // 是否检测到人脸
  yawDeg, pitchDeg,    // 头部真实角度（度）
  open,                // 睁眼度 0–1
  raw                  // 含 faceBlendshapes
}
```

#### 判定表

| 事件       | 判定条件                                    | 阈值    | 最短持续       | 说明              |
| -------- | --------------------------------------- | ----- | ---------- | --------------- |
| `AWAY`   | `present === false`                     | —     | **2000ms** | 人脸完全丢失，最确定的分心   |
| `DOWN`   | `pitchDeg < base.pitch - 22`            | 22°   | **2500ms** | 低头，大概率在看手机      |
| `UP`     | `pitchDeg > base.pitch + 18`            | 18°   | **2500ms** | 抬头看别处           |
| `TURN`   | `abs(yawDeg - base.yaw) > 30`           | 30°   | **2500ms** | 转头              |
| `GAZE`   | 眼内偏移超基线（自适应 ±3σ，见 **F10 G1**），或已校准时视线出屏 | 见 F10 | **2000ms** | 头没动，眼睛跑了        |
| `DROWSY` | `open < 0.35`                           | 0.35  | **1500ms** | 长时间闭眼           |
| `BLINK`  | 闭眼但 < 300ms                             | —     | —          | **不算分心**，自然眨眼豁免 |

> 📌 以上阈值的依据见 本文第三部分。**不要凭感觉改这些数字**，先读那份文档第 5 节。

> `base` = 会话开始后前 5 秒的姿态中位数，**每次会话重新采集**。用户换坐姿就要重来。

#### 状态机（每个事件类型独立跑一份）

```js
// 每个类型维护一个实例
function updateEvent(state, conditionMet, now, minDuration) {
  if (conditionMet) {
    if (state.since === 0) state.since = now;          // 开始计时
    if (!state.active && now - state.since >= minDuration) {
      state.active = true;
      state.start = state.since;
      onEventBegin(state.type, state.start);
    }
    if (state.active) {
      state.lastHit = now;
      state.quietSince = 0;
    }
  } else {
    if (state.active) {
      // 防抖：条件消失也要连续 1200ms 才认为真的结束
      if (state.quietSince === 0) state.quietSince = now;
      if (now - state.quietSince >= T.exitQuietMs) {
        state.active = false;
        onEventEnd(state.type, state.quietSince);
        state.since = 0;
        state.quietSince = 0;
      }
    } else {
      state.since = 0;                                  // 没够时长就消失了，作废
      state.quietSince = 0;
    }
  }
}
```

#### 关键设计原则

1. **单帧不判定**。人脸检测每秒都有 1–2 帧抖动，必须靠"最短持续"过滤。
2. **进入难、退出也难**。进入要 2.5 秒，退出要连续 500ms 干净，防止反复横跳。
3. **事件可重叠**。可能同时"低头"+"视线游离"，报告里按主事件归类（优先级 `AWAY > DOWN > TURN > UP > GAZE > DROWSY`）。
4. **暂停时不判定**。用户主动暂停期间一切都是合法的。

#### 专注率的计算

```js
// 分心总时长 = 所有事件时长之和（重叠部分只算一次）
const distractedMs = unionDuration(events);
const focusMs = actualMs - distractedMs;
const focusRate = focusMs / actualMs;
```

> ⚠️ 用**并集**算，不是简单相加。两个事件重叠时加两次会把专注率算低。

#### 代码位置

- 新建 `src/core/attention.js`：纯函数，**必须可单测**
  - `createEventTracker()`
  - `updateFrame(trackers, frame, base, now)`
  - `unionDuration(events)`
- 新建 `src/core/posture.js`：base 采集与头位判定

#### 验收标准

- [ ] 合成 frame（低头 30°）喂 3 秒 → 产生 1 条 DOWN 事件，`durMs` ≈ 3000
- [ ] 低头只喂 1 秒 → **不产生**事件
- [ ] 两个事件重叠时，`unionDuration` 不重复计算
- [ ] 会话暂停期间喂 frame → **不产生**任何事件

### F3 · 头位偏离统计（抬头 / 低头 / 转头）

#### 目标

单独统计姿态变化次数，用于报告里的"你抬头了几次、低头了几次"。

#### 与 F2 的区别

- **F2 是"分心判定"**：综合了持续性、其他信号，关心"这段是不是没在学"
- **F3 是"姿态统计"**：只数头动了多少次，不判断是不是分心

一次 10 秒的低头，在 F2 里记 **1 次分心**，在 F3 里记 **1 次低头**。但一次 1 秒的低头，F3 记 1 次，F2 不记。

#### 判定

复用 `base`，阈值比 F2 更宽松（因为只是计数，不扣专注率）：

| 方向 | 条件                            | 最短持续  |
| -- | ----------------------------- | ----- |

### F4 · 情绪状态分析

#### 目标

从表情推断 4 个维度的粗粒度状态，画成曲线放进报告。

#### 数据源

`frame.raw.faceBlendshapes[0].categories` —— 52 个 blendshape 分数。

用到的：

| blendshape                           | 含义         |
| ------------------------------------ | ---------- |
| `browDownLeft` / `browDownRight`     | 皱眉         |
| `mouthFrownLeft` / `mouthFrownRight` | 嘴角下撇       |
| `mouthSmileLeft` / `mouthSmileRight` | 嘴角上扬       |
| `jawOpen`                            | 张嘴（打哈欠/说话） |
| `eyeSquintLeft` / `eyeSquintRight`   | 眯眼         |
| `noseSneerLeft` / `noseSneerRight`   | 鼻翼皱起       |

#### 四个维度的计算

```js
const avg = (a, b) => (a + b) / 2;
const bs = (name) => categories[name] || 0;

const brow    = avg(bs('browDownLeft'),    bs('browDownRight'));
const frown   = avg(bs('mouthFrownLeft'),  bs('mouthFrownRight'));
const smile   = avg(bs('mouthSmileLeft'),  bs('mouthSmileRight'));
const squint  = avg(bs('eyeSquintLeft'),   bs('eyeSquintRight'));
const sneer   = avg(bs('noseSneerLeft'),   bs('noseSneerRight'));
const jaw     = bs('jawOpen');

// 挫败：皱眉 + 嘴角下 + 鼻翼
const frustration = clamp01(0.55 * brow + 0.30 * frown + 0.15 * sneer);

// 疲惫：闭眼 + 眯眼 + 打哈欠（张嘴）
const fatigue = clamp01(0.45 * (1 - frame.open) + 0.30 * squint + 0.25 * jaw);

// 投入：睁眼 + 不皱眉 + 微笑
const engagement = clamp01(0.45 * frame.open + 0.30 * (1 - brow) + 0.25 * smile);

// 困惑：皱眉 + 咬牙（用 jaw 近似）+ 眯眼
const confusion = clamp01(0.50 * brow + 0.30 * squint + 0.20 * jaw);
```

#### 平滑（必须做）

单帧表情噪声极大，**禁止直接画到曲线上**。

```js
// EMA 平滑，α 越小越稳
const ALPHA = 0.12;
state.frustration += (rawFrustration - state.frustration) * ALPHA;
```

或者用 3 秒滑窗取中位数（更抗尖峰）。

#### ⚠️ 诚实边界（必须写进 UI 和答辩）

**这不是情绪识别，是表情倾向估算。**

- 普通 RGB 摄像头无法可靠区分"皱眉思考"和"皱眉生气"
- 亚洲人脸的表情幅度普遍较小，blendshape 分数偏低
- 打哈欠和张嘴说话在数据上几乎一样
- **准确率不要写任何具体数字**，写"行为学估算，仅供参考"

在报告里必须标注：

> 情绪数据来自面部表情的行为学估算，不能作为心理状态判断依据。

#### 代码位置

- 新建 `src/core/emotion.js`：`computeEmotion(frame)` → `{frustration, fatigue, engagement, confusion}`
- 纯函数，可单测

#### 验收标准

- [ ] 输入全 0 的 blendshape → 四个维度都是有限值（不能 NaN）
- [ ] `frame.open = 0`（闭眼）→ `fatigue > 0.4`
- [ ] `browDown` = 1、其余 0 → `frustration > 0.5`
- [ ] EMA 平滑后，单帧尖峰不会让曲线跳变超过 0.2

### F5 · 专注度实时评分

#### 目标

把多个信号融合成一个 0–100 的分数，供实时显示和报告使用。

#### 公式

```js
// 各分量都是 0–1
const presentRatio   = 窗口内在座帧 / 总帧;        // 在座率
const gazeStability  = 1 - clamp01(|ex - base.ex| / thrX); // 视线稳定度（免校准，见 F10）
const headStability  = 1 - clamp01(头位偏离幅度 / 30); // 头稳不稳
const engagement     = emotion.engagement;         // 表情投入

const focusScore = Math.round(100 * (
  0.35 * presentRatio +
  0.25 * gazeStability +
  0.20 * headStability +
  0.20 * engagement
));
```


#### 窗口
滑动 **60 秒**，每秒重算一次。不要用全历史（反应太慢）。

#### 分级（用于界面配色和文案）

| 分数 | 状态 | 颜色 | 文案 |
|---|---|---|---|
| 85–100 | 深度专注 | 绿 | 状态很好，继续保持 |
| 65–84 | 正常专注 | 蓝 | 在轨道上 |
| 40–64 | 轻度分心 | 黄 | 感觉你有点飘 |
| 0–39 | 明显分心 | 橙 | 要不要先休息一下 |

#### 代码位置
`src/core/attention.js` 内 `computeFocusScore(window)`。

#### 验收标准
- [ ] 全程在座、头不动、表情中性 → 分数 > 85
- [ ] 全程人脸丢失 → 分数 → 0
- [ ] 分数变化不会单帧跳变超过 25 分（要平滑）

### F10 · 眼神注意力引擎（眼控保留下来的部分，用在这里）

#### 定位：眼控不是被砍掉，是换了工种

| | 旧主线（眼控产品） | 新主线（自律产品） |
|---|---|---|
| 眼睛的作用 | **输出**：代替鼠标点按钮 | **输入**：判断你有没有在学 |
| 关键动作 | 把眼球位置映射成屏幕坐标 | 读眼球相对眼眶的偏移、扫视节奏、眨眼节律 |
| 要不要校准 | 必须，否则点不准 | **基本不要**，只有出屏判定需要 |
| 代码 | `gaze.js` 九点校准 + 光标渲染 | 新增 `core/gaze-attention.js` |

理由很实际：**没有人会在开始 25 分钟学习之前先做 20 秒校准。** 所以自律场景里，凡是需要绝对屏幕坐标的信号都得降级；凡是**相对量**都能直接用。

而 `vision.js` 已经把相对量算好了，一行都不用改：

```js
// 虹膜相对「内外眼角中点」的偏移，用两眼平均眼宽归一化
// 注意：眼角中点不随眼睑开合变化，眨眼时不会跳
hxL, hyL, hxR, hyR   // 范围约 ±0.55，两眼方向已统一、共用同一尺度
```

这两个设计细节决定了它可用：**用眼角中点而不是眼眶包围盒**（眨眼不抖）、**两眼共用尺度**（头转动时近眼变大不会被误当成视线位移）。组员不用重做特征工程。

#### G1 · 眼头不一致（进专注率，最强的一个）

**原理**：人看屏幕时，头和眼的朝向基本一致。当"头还端坐着、眼睛已经跑了"（看手机、看旁边的人、发呆），眼球会持续偏向一侧且**不回来**。

**计算**（全程免校准）：

```js
// 两眼平均的水平/垂直眼内偏移
const ex = (frame.hxL + frame.hxR) / 2;
const ey = (frame.hyL + frame.hyR) / 2;
```

**前提门控**（很重要，否则头转动会污染判定）：

```js
// 只在这些条件成立时才评 G1；头转了交给 TURN 事件处理
const headSteady =
  Math.abs(frame.yawDeg   - base.yaw)   < 10 &&
  Math.abs(frame.pitchDeg - base.pitch) < 12;
```

**判定**：

```js
// 自适应阈值：用基线期标准差，避免不同眼型套同一个数
const thrX = Math.max(0.10, 3.0 * base.stdEx);   // 0.10 ≈ 半个虹膜宽度
const thrY = Math.max(0.09, 3.0 * base.stdEy);

const drift = headSteady &&
  (Math.abs(ex - base.ex) > thrX || Math.abs(ey - base.ey) > thrY);
// 持续 ≥ 2000ms → GAZE_DRIFT
```

`base.ex / base.ey / stdEx / stdEy` 用会话前 5 秒采集（和 F2 的 `base` 同一次采集，不要采两遍）。

**为什么要 2 秒**：一次正常看屏幕边角（看时间、看进度条）也会大幅偏，但会马上回来。**只有持续 2 秒不回来才是"眼睛跑了"。**

**判定不了什么**：眼睛偏 ≠ 一定在看别的东西，也可能在看屏幕上很边角的位置。所以 G1 只判定"视线脱离工作区"，不判定"在看手机"——那个归因交给 F4 的标签，不要写死。

#### G2 · 注视凝固（只做标签，不进专注率）

**原理**：人在真正阅读或看内容时，眼睛每秒跳 3–5 次（跳视 saccade）。**如果眼睛连续 8 秒几乎不动，说明它在"盯着"而不是在"看"——这是走神（mind wandering）最典型的生理特征，也是所有基于头部的方案完全看不见的。**

这是整个 F10 里最值得讲的信号：**头没动、眼没偏、但它知道你不在。**

**计算**：

```js
// 每秒归一化移动速度
const dt = (now - prev.t) / 1000;
const v  = Math.hypot(ex - prev.ex, ey - prev.ey) / dt;

const isSaccade = v > 1.0;      // 跳视：速度快、幅度大
// 注视漂移通常在 0.02–0.1/s，跳视在 2–5/s，两者差一个数量级，阈值很好定
```

**判定**：

```js
// 8 秒滑窗内跳视次数
if (saccadesInWindow < 5 && Math.abs(ex - base.ex) < thrX) {
  // 眼没偏 + 几乎不跳 → GAZE_STARE（盯着发呆）
}
```

**⚠️ 必须按任务类型开关**：看视频、盯图表时跳视天然很少，直接判定会大面积误报。所以 **F1 会话开始时让用户选任务类型**（阅读 / 写代码 / 看网课 / 刷题），G2 只在"阅读、刷题"下启用，其他类型只记录不判定。

#### G3 · 眨眼节律（只做标签 + 护眼，双向用）

同一个指标，两个方向指向两种完全不同的状态：

| 模式 | 眨眼率 | 伴随 | 结论 |
|---|---|---|---|
| 走神型 | **↑ > 25 次/分** | G2 触发、`engagement` 不低 | 眼睛在屏幕上，脑子走了 |
| 疲劳型 | **↓ < 8 次/分** | 平均 `open` 低、眨眼时长变长 | 该休息了 |

**为什么这条有价值**：走神时眨眼增多、疲劳时眨眼减少，两个方向都能读出来。只用"眨眼太少提醒护眼"是浪费了这个信号。

眨眼事件检测复用现有逻辑（`open` 从 >0.6 跌到 <0.3 再回升算一次），60 秒滑窗统计。

#### G4 · 视线出屏（可选增强，需校准）

只有这一项需要 `gaze.js` 的九点校准。作用：用户手动校准过就用，没校准就跳过，**不要为了它强制校准**。

```js
const g = gaze.getScreenPoint(frame);       // 需要已校准
const off = g.x < 0 || g.x > W || g.y < 0 || g.y > H;
// 持续 3000ms → 合并进 G1，不单独出事件
```

#### 质量门控（不做这个，噪声会毁掉一切）

MediaPipe 在 640×480 下虹膜直径只有约 10px，**1px 误差就等于 10% 眼宽**。所以：

1. **闭眼帧直接丢弃**：`open < 0.5` 或 `blinkL/blinkR > 0.4` 的帧不参与 G1/G2
2. **眯眼降权**：`eyeSquint > 0.4` 时眼睑遮挡虹膜，把该帧权重降到 0.3（不是丢弃，否则眯眼学习的人会被判成"无数据"）
3. **表情干扰降权**：皱眉严重时眼角点会被带动，`browDown > 0.5` 时同样降权
4. **平滑**：`ex/ey` 先过 3 帧中值滤波再算速度，否则单帧跳点会被算成跳视

> 第 2、3 条用的是 F4 的 blendshape 输出——**表情引擎反过来给眼神引擎做质量门控**，两个模块不是各自算各自的。

#### 微表情怎么用：只做归因，不做判据

**不要用微表情判定分心。** 皱眉可能是深度思考（好事），也可能是烦躁（坏事），同一个信号指向相反结论，用它判定必然反向。这一点在 本文 C1 有数据支撑（FER2013 上专用模型只有 59.28%）。

**正确的用法是给事件打标签**：当一个 `GAZE_DRIFT` / `GAZE_STARE` 事件结束时，回看事件前 10 秒的 F4 平均值：

| 事件前 10 秒 | 报告里写 |
|---|---|
| `frustration` 高 | 「这次分心前你在皱眉，可能卡住了」 |
| `fatigue` 高 | 「这次分心前你有点累，不是不专心」 |
| `confusion` 高 | 「这次分心前表情偏困惑，可能是没看懂」 |
| `engagement` 不低但 G2 触发 | 「眼睛一直在屏幕上，但没在扫视——走神了」 |

这个用法**安全且是加分项**：它把"你又走神了"这种指责，变成"你走神是因为卡住了"，产品态度完全不同。评委听到这句会记住。

### F12 · 肢体动作检测（Pose 33 点，只认四肢动作，不做角度精算）

#### 为什么要有这一节

眼睛和头能回答「在看哪」，但回答不了「身体撑没撑住」。有些状态根本不在眼睛上：

- 人还在学，只是**身体撑不住了**：伸懒腰、撑头、趴桌
- 人**已经不在桌前**：起身、走开
- **很长时间一动不动**：久坐

这三类只有肩线、手臂和躯干的相对位置能说明。Pose Landmarker 的 33 个关键点覆盖得到，模型 `vendor/mediapipe/pose_landmarker_lite.task` 已经下载在本地（5.8MB），和物体检测共用同一个运行时，不需要第二个推理引擎。

#### 一条红线：肢体动作**不进专注率**

这是本节最重要的一条，先写在最前面。

伸懒腰、托腮、抱臂、叉腰，全都发生在「人还在学」的时候。**把它们记成走神，用户会觉得"我一动它就说我没学"，这种不信任比漏判严重得多**（这条取舍的依据见 A10 与 B6）。

所以 F12 的产出只有两类：

| 产出 | 去哪 |
|---|---|
| 动作标签（伸懒腰 N 次、撑头 N 次、抱臂 N 次） | 报告里的「身体状态」一格 |
| 健康提醒（该起身了、趴太久了） | 就地提示，不进分数 |

**唯一进 F2 的只有离座。** 趴桌超时走的是「暂停会话」这条路径，而且必须让用户确认，不能悄悄扣分。

#### 精度要求：只要认得出动作，不要算得出角度

这一节刻意做粗，原因是画面条件不允许做细：

- 笔记本摄像头在屏幕上方、略微俯拍，**桌子会挡住髋部**，膝和踝几乎常年出画
- 凡是依赖髋部的量（躯干倾角、脊椎曲率）在这种画面下要么算不出来，要么抖到没法用
- 评委不会因为「躯干前倾 18.4°」多给一分，但一定会因为「我一抬手它就说我走神」不信这个产品

所以 F12 的定位是：**把四肢的动作认成名字**，不做姿态测量。

| 要 | 不要 |
|---|---|
| 手腕在不在肩线上方 | 手臂抬起了多少度 |
| 手腕离鼻子多近（除以肩宽） | 肘关节夹角 |
| 两腕是否交叉 | 精确的手部三维姿态 |
| 四肢这一秒动没动 | 位移速度数值 |
| 可见点在画面里的整体位置 | 身体重心、脊椎曲线 |

判据全部收敛成「比例大于某个数」「比例小于某个数」的二值比较，输出是动作名加时间戳，不输出角度。误报靠两道闸门压制，不靠反复调阈值：

1. **持续时长**：动作要维持 N 毫秒才算数，逐条写在动作表里
2. **三帧投票**：最近 3 帧里至少 2 帧成立才输出，单帧抖动直接丢掉

这两道闸门能挡掉绝大部分误报，而且不需要为每个动作单独标定。黑客松的排期里，标定一个角度阈值要一下午，投两行代码只要两分钟。

#### 输入：33 点里取 13 个

```js
pose = {
  t, present,
  kp: {          // 33 点里取 13 个，前 9 个是主力
    nose, lEar, rEar,
    lShoulder, rShoulder,
    lElbow, rElbow,
    lWrist, rWrist,
    lHip, rHip,      // 只在可见时用于叉腰、起身
    lKnee, rKnee,    // 只在可见时用于起身
  },
  vis: { lShoulder: 0.98, lHip: 0.42, ... },  // 每个点的置信度
  sw,            // 肩宽（像素），所有距离一律除以它做归一化
}
```

**归一化一律除以肩宽**，不要用屏幕尺寸。人凑近或后仰时肩宽会变，但它变的幅度和身体尺度一致，除完就稳定了。

#### 五个粗量

只有五个，全部是比值，没有一个需要开三角函数。

| 量 | 算法 | 用在哪 |
|---|---|---|
| `armUpL / armUpR` | `(肩中点.y − 腕.y) / sw`，单手一侧就可能为正 | 举手、伸懒腰 |
| `handToHeadL / handToHeadR` | `dist(腕, 鼻) / sw` | 撑头、托腮、摸头 |
| `handsCross` | 左腕 x 越过右肩 x，或右腕 x 越过左肩 x | 抱臂 |
| `headDrop` | `(鼻.y − 肩中点.y) / sw`，正常为负值 | 趴桌、含胸 |
| `limbEnergy` | 腕 + 肘 4 点在最近 10 帧（5 秒）内的平均位移 `/ sw` | 久坐、离开 |

`armUp` 直接取 y 方向的差，不算角度；`handToHead` 用欧氏距离除以肩宽，也不需要脸的角度。**这两个量对人脸朝向、身体远近都不敏感，这是它们比角度类指标更好用的原因。**

#### 动作表：八条判定

| 动作 | 判据 | 持续 | 产出 |
|---|---|---|---|
| `STRETCH` 伸懒腰 | **双臂同时** `armUp > P.stretchUp`（0.10） | 1200ms | 计数 |
| `ARM_RAISE` 单手举起 | 单侧 `armUp > P.raiseUp`（0.12），另一侧 < 0 | 800ms | 计数（多为示意/回答） |
| `WAVE` 挥手 | 腕 x 在 2 秒内往复 ≥ 3 次，单次幅度 > 0.3×sw | 2s 窗口 | 计数 |
| `HAND_ON_HEAD` 撑头 / 托腮 | `handToHead < P.handHeadDist`（0.55） | 2000ms | 计数 + 占比 |
| `ARMS_CROSSED` 抱臂 | `handsCross` 且两腕都低于肩线 | 1500ms | 计数 + 占比 |
| `HANDS_ON_HIPS` 叉腰 | 腕到同侧髋距离 < 0.5×sw，**髋可见时才算** | 1500ms | 计数（可选） |
| `LEAN_ON_DESK` 趴桌 | `headDrop > P.headDropLean`（−0.05） | 3000ms | 事件，超 3 分钟转 `REST` |
| `SEDENTARY` 久坐 | `limbEnergy < P.sedentaryEnergy` | 600000ms | 健康提醒，不进分数 |

再加一条只统计不出事件的：

**含胸 `HUNCH`（只算占比）**

```js
const hunch = headDrop > P.headDropHunch;   // 建议首版 −0.45，需实测
```

含胸就是头压得离肩线很近。正常坐姿下 `headDrop` 大约在 −0.6 到 −0.8 之间（每个人的肩颈比例不同），低头含胸时会收到 −0.4 上下。**不产生离散事件，只算 1 分钟窗口内的占比**：姿势是持续状态，逐次计数没有信息量（"你含胸 217 次"是废话），报告里给「含胸时间占 38%」才有用。

**这一条是全节唯一需要实测标定的量**，理由见后面「唯一的标定项」。

#### 为什么不再检测耸肩

上一版用「腕过肩 + 肩线上移」区分伸懒腰和举手。改成「双臂同时上举」之后，耸肩这个伴随条件可以删掉：

- 肩线上移需要维护一个静息基线，人被摄像头挪动一次基线就废了
- 真正区分两者的不是耸肩，是**几只手在动**。举手示意几乎都是单手，伸懒腰几乎都是双臂
- 少一个量，少一个要标定的阈值，少一类误报

代价是「单臂伸懒腰」会被记成 `ARM_RAISE`。这个代价可以接受，因为两者在报告里的权重都很低，都不进专注率。

#### 判定代码（可直接抄）

新建 `src/core/body.js`，全部是纯函数，不碰 DOM 也不碰摄像头，可以单测。

```js
const dist = (a, b) => Math.hypot(a.x - b.x, a.y - b.y);

// ① 一次算出五个粗量
export function measures(p) {
  const k = p.kp, sw = p.sw || 1;
  const smY = (k.lShoulder.y + k.rShoulder.y) / 2;
  return {
    armUpL: (smY - k.lWrist.y) / sw,
    armUpR: (smY - k.rWrist.y) / sw,
    handToHeadL: dist(k.lWrist, k.nose) / sw,
    handToHeadR: dist(k.rWrist, k.nose) / sw,
    handsCross: k.lWrist.x > k.rShoulder.x || k.rWrist.x < k.lShoulder.x,
    headDrop: (k.nose.y - smY) / sw,
    bothBelowShoulder: k.lWrist.y > smY && k.rWrist.y > smY,
  };
}

// ② 三帧投票：单帧抖动直接丢
export const vote = (win) => win.filter(Boolean).length >= 2;

// ③ 动作识别：输入当前量 + 三帧窗口，输出动作名或 null
export function classify(m, win, P) {
  if (vote(win.stretch)) return 'STRETCH';
  if (vote(win.wave)) return 'WAVE';
  if (vote(win.raise)) return 'ARM_RAISE';
  if (vote(win.head)) return 'HAND_ON_HEAD';
  if (vote(win.cross)) return 'ARMS_CROSSED';
  if (vote(win.lean)) return 'LEAN_ON_DESK';
  return null;
}
```

每个 `win.xxx` 就是一个长度 3 的布尔队列，每帧 push 一条、shift 一条。时长判定不放在 `classify` 里，而是放在上层：**同一个动作连续出现够 N 毫秒才落库**，落库后 2 秒冷却，防止一帧一次刷屏。

**挥手的判定要单独写**，它看的是横向轨迹的往复次数，不是一个瞬时量：

```js
// 环形缓冲保留最近 2 秒的腕 x，数变向次数
export function isWaving(buf, sw) {
  let turns = 0, dir = 0, amp = 0;
  for (let i = 1; i < buf.length; i++) {
    const d = Math.sign(buf[i] - buf[i - 1]);
    if (d !== 0 && d !== dir) { dir = d; turns++; amp = 0; }
    amp = Math.max(amp, Math.abs(buf[i] - buf[i - 1]));
  }
  return turns >= 3 && amp > 0.3 * sw;
}
```

#### 起身比离座早 1 到 2 秒

`present`（人脸是否在画面里）是 F2 判断离座的主要依据，但它总慢半拍：人得站起来走出画面，`present` 才翻成 `false`。

Pose 能提前看到动作。三个信号任意一个成立，先把状态标成 `STANDING`：

```js
const rising =
  (kp.lHip && vis.lHip > 0.4) || (kp.lKnee && vis.lKnee > 0.4)  // 髋或膝进画面（站起来位置变了）
  || shoulderMidYDrop > 0.5 * sw                                 // 肩线整体下移（起身时镜头相对下降）
  || (!present && limbEnergy > 0.02);                            // 人快出画了但还在动
```

`STANDING` 维持 2 秒后如果 `present` 仍为 `false`，直接推 `AWAY`，比纯看人脸快 1 到 2 秒。**这 1 到 2 秒很值钱**：离座是最容易讲的一个指标，反应越快越像「真的在看着你」。

注意肩线整体下移这个判断和人距离镜头远近有关，人往后退也会触发。所以它单独不成立，必须叠加「肢体仍在动」。

#### 门控与 `null` 约定

Pose 的下半身经常出画（桌子挡住），这是常态不是异常。

**任何依赖髋、膝的判据，在关键点不可见时必须返回 `null` 而不是 `false`。** 和眼动那一套同一条规矩：`null` 是「没法判断」，`false` 是「判断了，不是」。上层遇到 `null` 是跳过，遇到 `false` 才继续计时。

写成 `false` 的后果很具体：髋部出画的人会被判成「没在久坐」，久坐提醒永远不触发，而数据看起来一切正常。

**上面八条里，只有叉腰和起身的第三条依赖下半身。** 其余六条全部只用脸、肩、腕、肘，桌面场景下永远有得判。这是做粗的另一个好处：抗遮挡。

#### 唯一的标定项

除 `sedentaryEnergy` 和 `headDropHunch` 两个量，其余阈值都是「大量/很少」的粗分界，用建议值就能跑，不需要标定。

这两个要实测，方法一样：让 2 个人各正常学习 5 分钟，把 `headDrop` 和 `limbEnergy` 序列导出。

- `headDrop` 的基线在哪里。正常坐姿记录下来大约是多少，含胸低头时掉了多少。**如果两个人的基线差超过 0.15，就别做全局阈值，改成每人会话开始时取前 30 秒的中位数当基线，判「比基线低 0.2」。**
- `limbEnergy` 静息时有多大。**如果静息值就该有 0.005 以上，说明摄像头噪声偏高，`sedentaryEnergy` 要跟着放大，否则久坐提醒永远不触发。**

这两个量的标定加起来不到半小时，别拖到最后一天。

#### 性能

| 项 | 值 |
|---|---|
| 频率 | **1fps**（1000ms 一次）|
| 单帧耗时 | **实测 36.6ms**（软件 GL 悲观值），真机 GPU 约 20~25ms |
| 摊到 30fps 每帧 | 约 **1.2ms** |
| 为什么 1fps 够 | 最短的动作是挥手（2 秒窗口），挥手期间动态提到 5fps；其余动作都是秒级到分钟级，1 秒采一次完全够 |

**这里修正了初版的判断。** 初版写 2fps、10~15ms，实测是 36.6ms，2fps 意味着每半秒就要阻塞一整帧（33ms 预算），表现是页面每 500ms 顿一下。降到 1fps 之后摊薄只有 1.2ms，而且必须走 A4 的单槽队列，不能和物体检测挤在同一帧。

挥手是唯一对帧率敏感的动作。1fps 数不准往复次数，所以**挥手期间单独提到 5fps**（200ms 一次），用「上一帧检测到腕部横向快速移动就提高下一段频率」的方式动态调，其余时候保持 1fps。不要整体提速。

#### 隐私：这是最好讲的一块

只存 33 个点的坐标，可以还原成火柴人，**还原不出人脸**。报告里的骨架剪影就用这份数据画。

答辩可以直接说：*"我们连画面都没存，只存了一副骨架。"* 这句话比任何"我们承诺不上传"都硬。

#### 代码位置

- 新建 `src/vision-pose.js`：封装 `PoseLandmarker`，1fps（挥手期间 5fps），输出上面的 `pose` 对象
- 新建 `src/core/body.js`：纯函数，全部可单测
  - `measures(pose)` 一次算出五个粗量
  - `classify(measures, win, P)` 输出动作名
  - `isWaving(buf, sw)` 挥手（看轨迹往复，不看瞬时值）
  - `isStanding(pose, prev, now)` 起身预判
  - `postureRatio(windowPoses)` 含胸占比
- 事件枚举新增（见 B2.2）：`STRETCH` / `ARM_RAISE` / `WAVE` / `HAND_ON_HEAD` / `ARMS_CROSSED` / `HANDS_ON_HIPS` / `LEAN_ON_DESK` / `STAND_UP` / `SEDENTARY`
- 报告「身体状态」一格：伸懒腰 N 次、撑头 N 次、抱臂占比 X%、含胸占比 X%、起身 N 次

#### 验收标准

- [ ] 正常坐着写字 3 分钟 → `STRETCH`、`ARM_RAISE`、`WAVE` 各 **0 条**
- [ ] 真伸懒腰一次（双臂上举）→ **1 条** `STRETCH`，2 秒内重复帧不重复计数
- [ ] 单手举手 1 秒 → **1 条** `ARM_RAISE`，**不产生** `STRETCH`
- [ ] 挥手 3 秒 → **1 条** `WAVE`（不是 3 条，落库后有冷却）
- [ ] 单手托腮 3 秒 → **1 条** `HAND_ON_HEAD`
- [ ] 双臂抱胸 2 秒 → **1 条** `ARMS_CROSSED`
- [ ] 趴桌 3 秒 → **1 条** `LEAN_ON_DESK`；趴 3 分钟 → 会话转 `PAUSED` 并弹一次确认，**不继续累计专注**
- [ ] 含胸 10 秒 → **不产生事件**，只在报告里出现占比
- [ ] 起身走出画面 → `AWAY` 比纯人脸判定**早 1 秒以上**
- [ ] 髋部不可见 → 叉腰判据返回 `null`，上层跳过而不是记分心
- [ ] 单帧关键点抖动（手抖、模型抖动）→ **不产生任何事件**（三帧投票生效）
- [ ] 姿态 1fps 下，页面帧率下降 **< 2fps**（不能出现周期性卡顿）

## B6 · 风险与取舍

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| **阈值误判**（稍微一动就记分心） | 高 | 致命 | 最短持续 2.5 秒 + 退出防抖 1200ms + 眨眼豁免 300ms；现场用「灵敏度」滑杆可调 |
| **情绪数据难看**（一直是 0） | 中 | 中 | 表情分数低是常态，界面用文字不用数字；不画绝对值曲线，画相对趋势 |
| **排名被质疑** | 高 | 中 | 只用方案 A（超过自己），保留原始数据可现场核对 |
| **专注率算低**（重叠事件重复计算） | 中 | 高 | 必须用 `unionDuration`，并写单测 |
| **手机/镜头不好导致 present 频繁 false** | 中 | 高 | 人脸丢失 2 秒才判定；低置信度时暂停判定而不是记分心 |
| **演示时一直被判定分心** | 中 | 致命 | 准备「演示模式」：用合成数据跑完整流程，讲逻辑而非实时 |
| **虹膜点抖动**（F10 特征噪声大，640×480 下虹膜仅约 10px） | 高 | 中 | 3 帧中值滤波 + 3σ 自适应阈值 + 闭眼/眯眼/皱眉帧降权；G1 要求持续 2 秒，让噪声被时间平均掉 |
| **G2 在看视频时大面积误报** | 高 | 中 | 按任务类型开关（只在阅读/刷题下启用）；误报时退回"只打标签不进专注率" |
| **眼神数据被当成"监视"** | 中 | 高 | 界面上眼神指示只有三态、不显示原始数值；报告里措辞用"这一行盯了很久"不用"你在发呆" |
| **低头时虹膜不可见**（写字看书时摄像头只拍到头顶） | 高 | 中 | 低头时段只统计头姿和时长，不下眼神结论；界面标"当前角度看不到眼睛" |
| **三个模型同时跑掉帧** | 高 | 高 | 分频调度是硬要求（脸 30 / 物体 1 / 姿态 1）+ 单槽队列；帧率低于 20 立即关掉物体检测 |

### 最重要的取舍

> **宁可少判，不可误判。**
>
> 用户被错误记了 5 次分心，会立刻不信任整个产品。漏判几次没人会发现。
> **所有阈值优先调保守，其次才是灵敏。**

## C1 · 第一层：现成项目对比

### C1.1 · FocusTrack（最接近，建议重点参考）

`github.com/0AnshuAditya0/focus-track`

| 项 | 做法 |
|---|---|
| 情绪 | 自训 7 类 CNN（FER2013，28,709 张），准确率 59.28% |
| 眼睛 | Haar Cascade 检测双眼，算眨眼率、注视居中 |
| 分心判定 | **规则引擎**：情绪 + 眼状态 → Focused / Distracted / Drowsy |
| 输出 | Session dashboard：时间轴、productivity score、眨眼率曲线 |
| 示例结果 | 时长 1m18s，生产力 83%，专注 83.8%，分心 13.5%，困倦 2.7% |

**可借鉴**：
- 三态分类（专注 / 分心 / 困倦）而不是二分类——我们文档里 6 种事件，报告里可以归并成三态
- 输出「生产力分数」这个单一指标，比一堆数字更好懂
- 用规则引擎而不是端到端模型——和我们的选择一致

**不借鉴**：Haar Cascade 检测眼睛太老，我们用 MediaPipe 虹膜点，精度高一个量级。

### C1.2 · Concentration Tracker（权重公式可直接用）

`github.com/MadScie254/concentration_tracker`

MediaPipe FaceMesh + 三路信号融合：

```
concentration = 0.4 × gaze + 0.4 × head_pose + 0.2 × (not blinking)
```

**可借鉴**：这就是我们 F5 专注度公式的现成参照。我们的版本多了「在座率」和「表情投入」两项，可以对齐成：

```
focusScore = 0.35 × presentRatio + 0.25 × gazeStability + 0.20 × headStability + 0.20 × engagement
```

> 注意：他们的 0.2 权重给「不眨眼」不太合理——专注时本来就会减少眨眼，把不眨眼当加分会让「盯到眼睛发干」得高分。我们用「在座率」替代更合理。

### C1.3 · StudyEyes（参数最完整，三个数字必抄）

`github.com/SahilAGowda/study-eyes`

6 种行为状态 + 明确的工程参数：

| 参数 | 值 | 作用 |
|---|---|---|
| **眨眼豁免** | **300ms** | 自然眨眼不判分心 |
| **状态平滑** | **3 秒** | 防止瞬时瞟一眼就闪成"分心" |
| **容差边界框** | **外扩 30%** | 眼睛在框边缘不算看走 |
| 参与度打分 | 专注 +10 / 说话 +5 / 记笔记 +8 / 看别处 −5 / 无人 −10 / 手机 −15 | 滑动累计 |
| 窗口 | 60 秒滚动 | — |

**可借鉴**：
- **300ms 眨眼豁免必抄**——我们原文档漏了这条，会导致每次眨眼都触发状态跳变
- **3 秒平滑**比我原文档的 500ms 退出防抖更稳，建议提上来
- 60 秒滚动窗口与我们的 F5 一致

### C1.4 · 另外两个（参考价值较低）

- **Attention-Detector**（shubZk17）：SVM 图像分类，22,000 张图。做法黑盒、不可解释，不适合我们。
- **EngageVision**（Manoj-2702）：MediaPipe 头姿 + 注视，理念和我们最接近，但代码较旧、无报告体系。

## C2 · 第二层：现成算法与工程参数

### C2.1 · 面部指标的定义

| 指标 | 公式 | 用途 |
|---|---|---|
| **EAR**（眼纵横比） | `(‖p2−p6‖ + ‖p3−p5‖) / (2‖p1−p4‖)` | 眨眼、闭眼、打盹 |
| **MAR**（嘴纵横比） | 类似 EAR，取嘴部 6 点 | 打哈欠 |
| **头姿角** | solvePnP 或 transformation matrix → yaw / pitch / roll | 转头、抬头、低头 |
| **注视点** | 虹膜相对眼角归一化 → 回归 | 视线游离 |

**我们的优势**：`vision.js` 里 `yawDeg` / `pitchDeg` / `rollDeg` 已经是**真实角度**，不用自己解 PnP，直接能用。

### C2.2 · 一篇直接对口的论文（Zenodo, 2026）

《Real-Time Driver Drowsiness and Distraction Detection Using Facial Landmark Analysis》

| 参数 | 论文取值 |
|---|---|
| EAR 阈值 | **0.22** |
| MAR 阈值 | **0.50**（打哈欠） |
| 低头 pitch | **−15°** |
| 转头 yaw | **±25°** |
| 平滑 | EAR / MAR 做 **5 帧移动平均** |
| 触发 | **连续 15 帧**（≈0.5s@30fps）才报警 |

这篇的价值在于：**它用的也是 MediaPipe Face Landmarker**，和我们的技术栈完全一致，参数可以直接当起点。

论文自己也声明「没有标注数据集，因此不声称准确率 / 召回率」——这个态度值得学。

## C3 · 第三层：学术与行业阈值

### C3.1 · 视线偏离多久算分心

来自驾驶分心研究（超星慕课《驾驶员视觉分散特征识别》）：

| 结论 | 数值 |
|---|---|
| 正常状态下，视线 80–90% 时间在 **±12°** 范围内 | ±12° |
| 发生视觉分散时，只有不到 50% 时间在 ±12° 内 | — |
| 偏离 < 1 秒对表现影响不大 | 1s |
| **偏离 > 2 秒即判定为视觉分散** | **2s** |
| Blanco「红线」：偏离 > 9 次，或单次 > 2.5s | 2.5s |
| 汽车制造协会标准：2s，或 20 秒内 10 次 | 2s / 10 次 |

### C3.2 · 头部角度阈值

| 来源 | 低头 | 侧转 |
|---|---|---|
| 车载 DMS（商用方案） | > **30°**，持续 > 2s | > **45°**，持续 > 2s |
| Zenodo 论文 | **−15°** | **±25°** |
| 课堂专注度系统 | — | > **45°** 且持续 |

> 差异很大（−15° 到 30°，25° 到 45°），原因是**场景不同**。见下一节。

### C3.3 · 课堂场景的一条关键经验

来源：《课堂专注度识别系统技术解析》

> 「视线游移的阈值我调了很久，最后定为**单次游移超过 3 秒才算一次分心事件，低于 3 秒的快速扫视属于正常课堂行为**。」

这条直接说明：**正常人的视线本来就会不停扫动**，把任何一次偏离都算分心，产品必然废掉。

### C3.4 · 注意力持续时间（决定产品节奏）

| 研究 | 结论 |
|---|---|
| Bradbury (2016), *Advances in Physiology Education* | 持续注意力在 **10–15 分钟**达峰，**20–25 分钟后显著下降** |
| Ariga & Lleras (2011), *Cognition* | 短暂休息可让表现维持 **50 分钟**不衰减 |
| Kleitman (1982), *Sleep* | 人体存在 **90–120 分钟**的超昼夜节律 |
| Mark, Gonzalez & Harris (2005), CHI | 被打断后**回到原任务**平均 **23 分 15 秒**（同一研究：同日恢复平均 25 分 26 秒；外部打断 22 分 37 秒；恢复前平均先处理 2.26 件别的事） |
| 综述结论 | 成年人最佳专注区间 **20–45 分钟** |

**对本项目的用处**：
- 默认时长 25 分钟有据可依，不是随便定的
- 报告里可以引用「每次被打断，平均要 20 分钟以上才能重新接上原来那件事」作为解释性注脚（Mark et al., 2005）
- **不要做乘法估算**。「打断 7 次 × 23 分钟 = 2.5 小时」这种算法一算就崩：25 分钟的会话不可能损失 2.5 小时。而且原研究量的是"回到原任务的时间"，不是"恢复专注深度的时间"，两者不等价
- 90 分钟属于长会话，需要在报告里提示「已超出多数人的最佳区间」

## C4 · 关键：为什么阈值不能照搬

这是整份文档最需要理解的一节。同样是「转头 30 度持续 2 秒」，在不同场景下结论完全不同：

| 场景 | 误判的代价 | 漏判的代价 | 阈值策略 |
|---|---|---|---|
| **驾驶监控** | 误报烦人但无害 | **可能致命** | **从严**：宁可误报，绝不漏报（所以用 2s、−15°） |
| **课堂监测** | 老师误判学生，学生反感 | 漏掉走神的学生 | 中等，容许误差 |
| **学习自律（我们）** | **用户失去信任，直接卸载** | 少记几次分心，没人发现 | **从宽**：宁可漏判，绝不误判 |

**结论：我们的阈值必须比驾驶场景更宽松。**

一个用户被错记 5 次「分心」，会立刻觉得「这软件根本不准」，然后关掉再也不开。反过来，漏记几次，他自己心里也没数——**这就是不对称的代价**。

所以：

> **驾驶用 2s / −15° / ±25°，我们要更宽。**
> **但不能宽到没意义——参考课堂场景的 3s，加上 2.5s 的持续判定，是合理区间。**

## C5 · 最终推荐阈值表

综合三层调研，给出可直接落地的数值。**这是对开发文档第 3 节 F2 的修订版。**

```js
// src/core/thresholds.js
export const T = {
  // ── F2 分心事件 ──────────────────────────────
  awayMs:        2000,   // 离座（人脸丢失），驾驶/工程通用值

  downDeg:       22,     // 低头：介于 Zenodo 15° 与驾驶 30° 之间
  downMs:        2500,   // 持续判定，对齐驾驶 2s 与课堂 3s 的中点

  upDeg:         18,     // 抬头：抬头幅度通常小于低头，阈值收紧
  upMs:          2500,

  turnDeg:       30,     // 转头：比 Zenodo ±25° 宽，比驾驶 45° 严
  turnMs:        2500,

  gazeOffMs:     3000,   // 视线游移：直接采用课堂场景的 3 秒
  drowsyOpen:    0.35,   // 闭眼度（对应 EAR≈0.22 的 blendshape 等价）
  drowsyMs:      1500,   // 打盹要比分心更敏感，1.5 秒就提醒

  blinkForgiveMs: 300,   // ★新增 自然眨眼豁免（StudyEyes）
  exitQuietMs:   1200,   // 退出防抖：从 500ms 提到 1200ms，防止反复横跳
  smoothFrames:  5,      // 5 帧中值平滑（Zenodo 论文做法）

  // ── F3 头位统计（只计数，不进专注率，可更宽松）──
  postureUpDeg:  14,
  postureDownDeg: 18,
  postureTurnDeg: 25,
  postureMs:     800,

  // ── F4 情绪 ─────────────────────────────────
  emaAlpha:      0.12,
  emoWindowMs:   3000,

  // ── F5 专注度 ────────────────────────────────
  scoreWindowMs: 60000,

  // ── 基线采集 ─────────────────────────────────
  baseSampleMs:  5000,
};
```

### C5.1 · 与初版开发文档的差异

| 参数 | 初版 | 修订 | 原因 |
|---|---|---|---|
| `turnDeg` | 25° | **30°** | 25° 是驾驶级敏感度，学习场景看旁边屏幕就会误判 |
| `downDeg` | 18° | **22°** | 低头记笔记也在这个区间，太松会误判「记笔记=走神」 |
| `gazeOffMs` | 4000 | **3000** | 课堂实测 3 秒足够，4 秒会让分心漏统计 |
| `drowsyMs` | 3000 | **1500** | 打盹是强信号，应更早提醒 |
| `exitQuietMs` | 500 | **1200** | StudyEyes 用 3s 平滑，500ms 太短会抖 |
| `blinkForgiveMs` | — | **新增 300** | 原方案漏了眨眼豁免，会导致每次眨眼触发状态跳变 |

### C5.2 · 头姿基线怎么取

所有角度都是**相对值**，不是绝对值。因为每个人坐姿不同：

```js
// 会话开始后前 5 秒，取俯仰角中位数作为零点
base.pitch = median(frames.slice(0, 150).map(f => f.pitchDeg));
base.yaw   = median(frames.slice(0, 150).map(f => f.yawDeg));
```

之后用 `pitchDeg - base.pitch` 判定。**换了坐姿就要重新取基线**，否则整套判定失效。

## C6 · 判读方法选型：为什么用规则引擎

调研里有两类做法：

| 做法 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| **规则引擎** | FocusTrack、StudyEyes、Zenodo 论文、车载 DMS | 可解释、可调参、不需要训练数据、单帧开销可忽略 | 阈值要手工调 |
| **端到端分类模型** | Attention-Detector（SVM）、FocusTrack 的情绪部分 | 省事 | 黑盒、不可解释、需要大量标注 |

**我们选规则引擎，三条理由：**

1. **没有标注数据**。我们没法收集"这是分心、这是专注"的标注集去训练。
2. **答辩要能解释**。评委问"你怎么判断我在分心"，能回答"你的头部俯仰偏了 22 度，持续 2.5 秒"——这比"模型输出 0.73"有力一百倍。
3. **现场要能调**。演示时如果误判，改一个数字就能修好；模型只能重训。

### 混合策略（可选，时间够再做）

课堂系统的做法值得借鉴：**规则处理高置信度，分类器处理模糊场景**。

- 高置信度（人脸消失、低头 30°、闭眼 1.5s）→ 规则直接判
- 模糊场景（头偏 5°、视线轻微偏移）→ 不判分心，只在分数上扣一点

我们的 F5 专注度分数天然承担了「模糊场景」的表达：不判事件，但分数会下降。**这已经是混合策略了，不用额外做分类器。**

## C7 · 可以直接写进报告的三个"硬数字"

这些有文献支撑，比自造指标有说服力：

1. **「被打断后平均要 20 分钟以上才能回到原来那件事」**（Mark, Gonzalez & Harris, 2005, CHI）
   用法：**只做定性说明**，不做时间乘法。原话是"回到原任务"，不是"恢复专注深度"。另注意常被误引为 Mark et al. 2008，那篇讲的是"被打断后速度更快但压力更高"，不是 23 分钟

2. **「成年人最佳专注区间 20–45 分钟，20–25 分钟后注意力显著下降」**（Bradbury, 2016）
   用法：解释为什么 25 分钟一轮，以及超过 45 分钟要提示

3. **「短暂休息能让表现维持 50 分钟不衰减」**（Ariga & Lleras, 2011）
   用法：鼓励用户真的去休息，而不是继续刷手机

```
1440×900 的浏览器窗口，真实视口高度只有 807px
（剩下的是标签栏和任务栏）

三栏高度预算（807px 视口）：
  顶栏 40  +  主区 580  +  时间轴 97  +  间距/内边距 90

右栏三张卡的高度预算：
  当前状态 218  /  传感信号 246  /  一句结论 88   = 552（正好等于可用空间）
```

**这是踩过的坑**：按 900px 排版，右栏第三张卡会被裁掉 151px。**任何改动都要在这个预算里做，超出就压缩内容，不要靠滚动。**

### D3.5 · 三个已经踩过的坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **CSS `filter` 用在 SVG 上** | 进度弧完全不渲染（尤其无 GPU 环境） | 用"宽描边低透明度 + 细描边渐变"两层画光晕，不依赖滤镜 |
| **`transition: .26s ease` 全局** | 切换按钮出现白底白字 | 只对 background-color / box-shadow 做过渡，颜色即时切换 |
| **`.metrics span{display:block}`** | 单位"次"被挤到第二行 | 选择器写 `.metrics>div>span`，别用后代选择器 |

## D4 · 数据契约（最重要的一节）

`demo-session.html` 里只有一个状态对象 `S`，**所有渲染函数都读它**。你只要让 `S` 变成真的，界面就全对了。

```js
const S = {
  remain,       // 剩余秒数         ← session.js
  running,      // 是否在计时       ← session.js
  score,        // 0-99 专注分      ← core/attention.js
  blocks,       // 60 格颜色历史    ← 每 5 秒 pushBlock()
  distract,     // 分心次数         ← F2 事件计数
  gazeCount,    // 走神次数         ← core/gaze-attention.js
  awaySec,      // 离座秒数         ← present=false 累计
  streakMax,    // 最长连续秒数     ← F5 连续 ≥65 的时长
  blink,        // 眨眼率 /分       ← health-monitor.js
  dist,         // 视距 cm          ← frame.distanceCm（低头时置空，见下）
  gaze,         // stable|drift|stare ← core/gaze-attention.js
};
```

对象里没有 `scene`，也没有 `hand`。界面不选场景，也不看手。

### 低头时视距要降级

`frame.distanceCm` 是基于**瞳距**估的。低头写字时瞳距被压缩，会算出"距离 90cm"这种假数据。

```js
// 低头超过 25°，视距直接标不可信，UI 显示 "--"
const distOk = Math.abs(frame.pitchDeg - base.pitch) < 25;
S.dist = distOk ? frame.distanceCm : null;
```

不修这条，护眼数据就是假的。**宁可显示"--"，也不要给一个错数。**

### 渲染函数不用重写

`updateRing()` / `updateHUD()` / `renderSignals()` / `pushBlock()` / `level()` 全部可以直接复用。**你只需要把 `simulate()` 删掉。**

## D5 · 接线步骤（具体到文件）

### 第 1 步：`src/core/attention.js`（F2 事件引擎，纯函数）

```js
export function classifyHead(pitch, yaw, base, T)          // down | up | turn | null
export function detectGazeDrift(ex, ey, base, T, now)       // 眼头不一致（G1）
export function detectDrowsy(eyeOpen, now, T)               // 打盹
export function cooldown(events, type, now, ms)             // 同类事件冷却
export function unionDuration(events, winStart, winEnd)     // 专注率去重，必须可单测
```

规则：**不依赖 DOM、不依赖摄像头**，输入普通对象、输出普通对象。这样能进 `tools/test-core.mjs` 跑单测（现在已有 52 项，接着加）。

三件事最容易写错，先把它们做对：

1. **事件冷却**。同一个 `TURN` 不能在 3 秒内记 5 次，否则用户转一次头就被扣 5 次。
2. **重叠去重**。低头和视线游移同时发生时，`unionDuration` 只能算一次时长，不能相加。不写这条，专注率会低到没法看。
3. **眨眼豁免**。眨眼 300ms 内不判任何事件，否则每眨一次眼都会触发一次状态跳变。

### 第 2 步：把 demo 换成真数据

```js
// 1. 删掉这些
- function simulate() { ... }
- setInterval 里的 simulate()

// 2. 换成
const sess = new Session({ minutes: 25 });
sess.on('tick', (snap) => {
  S.remain    = snap.remain;
  S.score     = snap.focusScore;      // core/attention.js
  S.distract  = snap.distractCount;
  S.gazeCount = snap.gazeCount;       // core/gaze-attention.js
  S.streakMax = snap.streakMax;
  S.gaze      = snap.gazeState;       // stable | drift | stare
  updateRing(); updateHUD();
});
setInterval(renderSignals, 900);      // 这一行保留

// 3. 每 5 秒
if (sec % 5 === 0) pushBlock();
```

**注意**：`S.blocks` 是 60 格的滚动窗口，`pushBlock()` 里已经处理了取模，不要自己再写一套。

## D6 · 产品规则（不能改，改之前先问）

| 规则 | 内容 | 为什么 |
|---|---|---|
| **不设场景选择** | 用户点开始就开始，界面上不出现"纸质/电脑"这类选项 | 多一次选择就多一次放弃 |
| **情绪只做"面部状态占比"** | 报告里写"平静 78%、皱眉 15%"，不写"压力指数" | 最好的开源模型只有 63% |
| **不做时间乘法** | 不写"打断 7 次 × 23 分钟 = 损失 2.5 小时" | 25 分钟的会话不可能损失 2.5 小时 |
| **文案不说"你在发呆"** | 说"这一行盯了很久"、"视线离开屏幕 1 分 40 秒" | 指控性措辞会让人关掉功能 |
| **阈值宁可松不可紧** | 分心判定全部先调保守 | 用户被错记 5 次就卸载 |

## D11 · 三个要先验证的假设

按风险排，第一条不成立，后面全部作废。

1. **真人脸下虹膜偏移能不能分出「在屏幕内」和「飘出去」。** 这是 F10 的地基。验法：打开摄像头，盯屏幕四角各 2 秒，把 `ex / ey` 序列导出，看四个角能不能分开。分不开说明光线或分辨率不够，先解决硬件。
2. **转头和低头会不会互相干扰。** 人转头时 pitch 也会跟着变，如果两者串了，`DOWN` 和 `TURN` 会互相触发。验法：只转头不动脖子看 pitch 是否漂移，只低头看 yaw 是否漂移。串了就先做一次头姿补偿。
3. **单个笔记本能同时跑人脸 + 姿态 + 物体。** 已实测：姿态 36.6ms、物体 88.6ms，人脸本身 10~20ms。结论是频率必须降、且不能同帧叠两个大模型（见 A4 单槽队列）。真机 GPU 下会更快，但仍要按队列写。
4. **姿态模型能不能看到肩和手腕。** 只认动作的方案里，六条判据只用脸、肩、腕、肘，髋和膝只在叉腰和起身预判里用到，出画就返回 `null`，不影响主链路。所以要验的只剩一件事：打开摄像头把 33 点画出来，看**肩和手腕**在不在画面里、抖不抖。肩腕稳定，F12 就能全部做完；如果腕部点也经常丢，说明摄像头角度太仰，把笔记本盖子往前压一点就能解决。
